# Claude Instructions for Grassroots Networking

## Working Style
Always be precise, critical, and helpful. Prefer to ask rather than assume if you have unclarities.

## Project Philosophy

Grassroots Networking is a **peer-to-peer messaging transport** — a thin layer that moves packets between devices over Bluetooth (BLE) and the Internet (UDP). It is not an application; it is the plumbing that applications like GSG build on top of.

**Core principles:**

- **Opportunistic mesh delivery (BLE).** Over Bluetooth, messages reach the recipient by multi-hop **request-driven conveyance**: nothing is ever pushed. Every node takes packets into custody — TTL-bounded and deduplicated — and hands one onward only when a neighbour's sync filter shows that neighbour has not seen it. Nodes **store-carry-forward**, holding packets for recipients that are currently out of range and conveying them when they reappear. This lets a user message a friend (or continue an existing chat) even when that friend is not a direct BLE neighbor. The Internet (UDP) transport stays **direct** point-to-point — it never relays for a third party — but it does hand a connected peer the buffered packets addressed to that peer (see Store-carry-forward). Either way the message *content* only ever exists in the clear on the two endpoints — relays forward sealed bytes addressed by recipient ID (see Mesh Envelope & Trust).
- **Identity is a key pair.** Every device holds an Ed25519 key pair. The public key *is* the peer's identity — nicknames are cosmetic. All trust decisions flow from cryptographic verification.
- **Two transports, one interface.** BLE covers nearby peers without Internet; UDP covers the globe. Both transports surface the same abstraction to the coordinator: connect, send, receive, disconnect. BLE is preferred when both are available.
- **Clean breaks, not compatibility shims.** When refactoring, fully replace old code. No legacy wrappers, no "kept for compatibility" comments, no dead code. Update every call site. There are no installed apps in the wild — you are free to rename, restructure, and break wire formats whenever it improves the design.

## No Legacy or Compatibility Code

When refactoring, DO NOT keep old code "for legacy" or "for compatibility". Fully replace old implementations, remove unused imports and dead code, and update all call sites. Use the Redux store (`AppState`) exclusively for shared state — no mutable singletons.

This applies to **wire-format decoders too**: when you add a field to a packet, do not write the decoder to "gracefully handle truncated/old payloads where the field is missing." There is no old version in the wild — the new field is required, and a payload that lacks it is malformed and must throw. Tolerance for a hypothetical previous version is a compatibility shim by another name.

## Opportunistic Mesh & Store-Carry-Forward (BLE)

The Bluetooth transport is an **opportunistic mesh**. Delivery is multi-hop and works in two cooperating ways:

- **Request-driven conveyance (open relay, NO FLOOD).** Nothing is pushed at a node that is not the recipient. A node that receives a packet not addressed to it decrements the TTL once, drops it at zero, and takes it **into custody**; it hands that packet to another **relay** only when that neighbour's sync filter shows it has not seen it. An age-bounded exact set of seen packet IDs (`SeenPackets`) prevents loops and re-processing. Relaying is **not** friend-gated: a node carries packets for recipients it has no relationship with — it only ever sees the recipient ID, never the sender or the content. That is what makes the mesh reach beyond direct neighbors. Nothing is rebroadcast at relays on first sighting: pushing a packet whether or not anyone lacks it is exactly the redundancy the request-driven path exists to remove.

  **The recipient is the exception, and a carrier delivers to it immediately.** A relay holding a packet for a peer it is directly connected to writes it on that link at once, exactly as the originator does, instead of waiting for that peer's next sync filter. The destination is the one node that cannot be sent a copy it did not want: it either lacks the packet or drops it on its own seen-set, so the redundancy argument that governs relay-to-relay traffic does not apply to the last hop. Custody is kept anyway — a successful write is not an end-to-end ACK — so the packet stays conveyable if that hop turns out to have been the wrong one. What this costs is bounded last-hop duplication: every carrier that holds the packet and is linked to the recipient will write it, and the recipient dedups the rest. What it buys is the latency the request-driven path otherwise adds to a message whose recipient is already in range.
- **Store-carry-forward (DTN).** Every transit packet with TTL left is **cached** by the node that receives it, in a bounded, age-expiring in-memory store — the **DTN memory buffer**, `DtnStore._byRecipient`, a map from recipient pubkey hex to the sealed packets held for them — and conveys it onward whenever a neighbour's seen-filter shows that neighbour lacks it. A node stores a transit packet whether or not the recipient is currently reachable: with nothing pushing, a packet a node does not keep is one it can never convey onward, so it would die there. Intermediaries thus hold other peers' traffic — but only as opaque, recipient-addressed, end-to-end-sealed bytes they cannot read. The buffer is memory only: it does not survive a process restart. **TTL bounds carrying**, and the rule is the same on every path: a node refuses a relay whose count has ALREADY reached 0; anything above that is accepted, decremented once, and forwarded. So a packet arriving at 1 is still passed on, going out at 0 — worth doing precisely because the destination is exempt from the refusal, so that last broadcast can still be accepted by a neighbour who is the recipient. Exhaustion never deletes anything: the packet stays in custody and remains conveyable at every sync exchange, leaving the buffer only on ACK, eviction or age. The two thresholds are tested against different values, because they are different acts: **delivering is judged on the TTL as it arrived and needs only >= 0**, so a packet reaching the node it is addressed to with nothing left is still delivered, while **forwarding subtracts one first and needs the result above zero**. The decrement happens ONCE per arrival, at the node that receives the packet — the sender never decrements. What a relay buffers is therefore the already-hopped copy, and a conveyance sends it unchanged: charging again on the way out would make one hop cost two and retire packets early. Nothing unforwardable reaches a buffer in the first place, since a packet that cannot be forwarded on arrival is dropped rather than stored. The one exception is arrival — a packet whose TTL runs out at the node it is *addressed to* is still delivered, because TTL bounds how far a packet may travel and this one has nowhere left to go. Without that hop cost the carry path sat outside the bound entirely, and every carried delivery reported zero hops, making a delivery that crossed the mesh in someone's buffer indistinguishable from a direct one.

**The sender falls back to that same DTN memory buffer**, so where it cannot deliver now it is just the first node holding the packets (which is what the madGLP "fair message delivery" assumption asks for, `docs/GLP_Networking_API/sections/api.tex` §Networking Assumptions). A send direct-writes to the recipient when that recipient is a connected neighbour, and **only what that write could not place goes into the buffer** — where it is conveyable in every sync exchange and is dropped only on the recipient's end-to-end ACK (or age expiry). Confirmations follow the same rule: an ACK or read receipt to a connected neighbour goes straight out, and is buffered when it cannot. There is **no separate sender-side retry queue, ACK-timeout re-queue, or periodic drain** — redelivery happens exclusively through the sync exchange, which runs both on connect and on every announce cycle (debounced per peer) for as long as the session lasts. Pairings are **eager**: every accepted ANNOUNCE leads directly to a Noise handshake — **any sessionless side initiates** (glare is resolved by the msg1 pubkey tie-break plus validate-then-commit message reads, so one-sided session loss always self-heals), and everything that moves buffered packets to a peer — sealing held messages, the sync vector exchange — is gated on that session existing, never on the raw link. **The sync exchange is the only way a buffered packet reaches a node that is not its recipient**, and it runs over **both** transports — but the two are answered with different sets. The peer advertises a compact filter of what it has seen; over **BLE** we answer with anything we hold, for any recipient, and over **UDX** only with packets addressed to **that peer**. The Internet therefore hands a node its own traffic and never third-party transit: a relay's held backlog stays on the radio side.

**The UDX restriction is about volume, not trust.** BLE encounters are sporadic and airtime is scarce, so the medium itself bounds the open relay. A UDX link is continuous and fast, and answering it with the whole buffer would push a 512 MiB store at every connected friend at link speed — turning well-connected nodes into exactly the infrastructure that removing the rendezvous servers deleted. Delivering to the endpoint on the other end of the link costs only those packets, so that is the part UDX gets. It is **not** a friend gate: conveyance is for everyone, and the friend-scoping on UDX is emergent (UDX links only exist between friends) rather than a rule. It needs no new trigger either — ANNOUNCE already goes out over UDP on the same `_announceTimer`, so the Internet path re-asks on the cycle the radio one does. The debounce is keyed per **(transport, peer)**, so a BLE round never suppresses the UDX one for a peer that is both in range and online. Direct sends over UDP are unaffected — the buffer exists precisely for recipients that were unreachable at send time. Never blind-push held packets on connect — the holder cannot know what the peer already has, and the measured cost of guessing wrong was ~32 redundant packets per reconnection (31% of confirmation bytes on the air in a 90-cycle soak).

**The asker advertises what it has SEEN; the holder answers by conveying what that filter is missing.** The exchange is a single directed frame per peer per round — a GCS compact filter over the asker's seen-set, carrying a time window `[fromMs, toMs]` — and there is **no reply frame, no decline ledger, and no open-round bookkeeping**. A converged pair falls silent by construction: the holder computes an empty difference and sends nothing, so nothing has to be inferred from silence, and no incomplete-round bookkeeping is needed.

Advertising SEEN rather than HELD is the load-bearing choice. A held-filter re-pushes the backlog at a node that already delivered a message and dropped it — it effectively says "I hold nothing, send me everything" — which measured 12.76 copies/msg on the air. The seen-set outlives the buffer, so an emptied node still says "I have seen these" and the holder conveys nothing it already handed on. A node that has genuinely seen nothing advertises an **empty filter over all time**, which is exactly right: a fresh or restarted node wants the whole backlog.

The window is what keeps a partial filter safe. One frame holds at most `GcsFilter.maxElements` ids, so the filter usually covers a slice of the seen-set rather than all of it — and the holder therefore answers **only from packets whose creation time falls inside the window**, never from the rest of its buffer. The asker sweeps a cursor across its seen-set and wraps at the end, so successive announce cycles cover everything. Two bounds ride along: the filter's 1/128 false-positive rate can silently withhold a packet, and `_maxConveyPerFilter` caps a single round at 64 packets — in both cases the remainder is not lost, it is simply picked up on a later sweep.

Originators buffer their **confirmations too**: ACKs and read receipts are sealed and put in their originator's buffer like any other recipient-addressed packet — they ride the sync exchange out, and (since nothing ACKs a confirmation) leave the buffer only by age expiry. **A duplicate of an already-delivered message triggers nothing**: no re-delivery, no re-ACK — dedup means drop, full stop.

**One leg per peer per write.** A converged pair holds two GATT legs, but a conveyance writes the packet on exactly ONE of them — preferring our peripheral leg (notify: unacknowledged at ATT level, several per connection interval) over the central leg (write). Sending on both put the same bytes on the air twice for the same peer and the receiver's packetId seen-set simply dropped the second copy: double airtime and battery for zero delivery benefit. The second leg is still maintained (it is the pair's other direction and its redundancy on failure), just not written to twice for the same packet.

That redundancy is **used**: a write refused on the chosen leg is retried on the pair's other one, and only then is the neighbour reported unreached. This is not the double-send the rule forbids — the fallback runs only after a throw, and on both platforms a throw happens *before* any byte reaches the controller (Android refuses while validating the path or when `notifyCharacteristicChanged` will not take the buffer; iOS on `valueTooLarge` or a full pending queue), so the packet cannot go out twice. The retry is skipped when the other leg's MTU cannot hold the packet — the two legs negotiate separately, and retrying onto a leg that truncates puts an unparseable write on the air while reporting success — and when the path is unidentified, since without a pubkey there is no way to tell the pair's other leg from a stranger's. It matters most on the preferred leg: the peripheral/notify path has no queue behind it at all, so it is the one that refuses under load, and an unretried refusal loses the packet for that neighbour.

**A PACKET MAY NOT EXIST BEFORE A SESSION WITH ITS TARGET DOES.** This is an invariant, not a preference, and it is enforced by ordering: the send path checks `hasSession` and returns without ever calling `createMessagePacket` if there is none. **The send path does NOT establish sessions** — it only refuses. Pairing is eager and lives where it belongs: every accepted ANNOUNCE drives a Noise handshake, any sessionless side initiates, and by the time a user can address a peer the session either exists or that peer is not someone we can talk to. Handshaking from inside send would put session setup on the message-latency path and, worse, make *sending* the act that decides who we have met. There is no plaintext hold in front of the sealed buffer: a message to a peer we have never handshaked with is FAILED, immediately and visibly, and the user retries when that peer is actually there. Holding an unsealed payload to seal it later is exactly the thing this design refuses — it put a readable message body in memory on behalf of a peer that might never appear, and it made "we created a packet for someone we never met" representable. It is not. The gate is the SESSION and never the peer record: the stale sweep deletes a non-friend from `peersList` after ten silent announce cycles while its Noise session survives untouched, so a recipient that has merely gone quiet has no record and is still perfectly sendable — `hasSession` short-circuits the establish and the message seals and goes into the buffer. That quiet-peer case is precisely what store-carry-forward exists to serve, and gating on the record broke it (measured 2026-08-10: 34 consecutive sends to a quiet peer, every one held, none buffered).

Bound what an attacker or a runaway loop can grow: the DTN memory buffer is capped on recipient count, **buffer-wide BYTES (512 MiB)** and age — deliberately NOT a per-recipient depth, which would silently drop a busy peer's oldest packets while the buffer as a whole sat nearly empty, and pin held confirmations at the cap. The size bound is bytes rather than a packet count because a count says nothing about memory unless every packet is the same size, and a fragmented message is several packets of whatever the MTU left over. It counts sealed payload bytes, not the object overhead around each entry, so real process memory sits above the figure — on a 2 GB handset the per-app heap limit is reached long before this ceiling is, and the OOM killer becomes the effective bound. There is **no per-neighbour relay rate cap**: at any rate low enough to bound abuse it shapes delivery instead, filling the drop table with `sync/budgetExhausted`. What bounds conveyance is TTL (strictly decremented, one hop per arrival) and the packetId seen-set (each packet conveyed onward at most once); a rate ceiling on top of those cost messages without buying a bound the other two did not already give. The **packetId index of what we hold** is bounded BY THE BUFFER: an entry leaves when its packets leave, for any reason — ACK, age expiry or eviction — because the store reports every non-ACK exit and the index applies it. Draining that index on ACK alone is not a bound at all: the buffer sheds packets for three reasons, so an index that knows about one fills with entries whose packets are already gone and then evicts LIVE ones — which switches ACK-driven release off and leaves those packets to age out, keeping the buffer full. Enlarging the cap does not fix this; it only postpones it. A count cap is NOT a universal requirement, though, and must never be bolted onto state whose job is correctness: delivery dedup is bounded by AGE alone (an id is kept until no copy of that message can still exist anywhere), because a count cap there evicts ids while copies are still in flight and re-delivers a message the app has already been handed — which is exactly what a periodic bloom rotation does.

**The Noise session table is the one deliberate exception, and it is deliberate — do not "fix" it by adding a cap.** Sessions are keyed by peer identity and survive the link that formed them, so the table grows with every peer the device has ever handshaked with, and `trialDecrypt` walks it once per inbound sealed packet. This is affordable because the envelope keeps its recipient field: other peers' traffic is rejected on a header compare before the loop is reached, so only packets addressed to us are ever trial-decrypted — ~1.75% of a core at 50 msg/s on a Nexus 5X, independent of table size (MRU-first finds the sender on the first attempt). The residual exposure is memory, not CPU. A cap would become **mandatory** only under a design that put transit packets through trial-decrypt — which is exactly why removing the recipient field was rejected: at 350 µs per failed AEAD open on a 5X, a transit packet costs S × 350 µs, saturating a core at 22 pkt/s with 128 sessions. What IS reaped: handshake entries older than twice the handshake timeout that hold no session, since nothing else removes a handshake nobody is awaiting. `trialDecrypt` also walks most-recently-used first, so conversational traffic hits on the first attempt rather than after S/2 failures. The measurement tooling is built and idle — `CryptoBench` for the device constants, `analyze.py session_cap()` and `contact_trace.py` for the re-encounter distribution. ANNOUNCE is **not** relayed onward; it stays neighbor-local (presence, not reach).

## Mesh Envelope & Trust

A relayed packet's **outer envelope carries only the recipient ID** (plus type, TTL, packet ID, length, and the originator's creation time — the last is what the sync window is computed over, and it tells a carrier the AGE of what it holds). It does **not** carry the sender — the sender's identity and the message body live inside an **encrypted envelope sealed to the recipient's Noise session**, readable only by the recipient. Consequences that are load-bearing for the whole design:

- **No cleartext sender, no per-packet Ed25519 signature on the wire.** The header carries no sender pubkey and no whole-packet signature. A relay cannot tell who originated a packet, and therefore **cannot authenticate it** — relaying is unverified by construction. This is the accepted cost of sender-anonymity; it is bounded by TTL and dedup, not by hop-by-hop signatures.
- **Authentication is end-to-end, inside Noise.** The recipient trusts a message because it decrypts under a Noise session whose peer static key was verified during the handshake. The peer's Ed25519 identity is conveyed **inside the encrypted handshake payload** (not in any cleartext header) and checked against the Noise static via the birational map (`docs/GLP_Networking_API/sections/ip.tex` §IP Connection). Because the outer envelope has no sender, the recipient demultiplexes an inbound sealed packet by **trial-decrypting** against its active sessions; the AEAD tag identifies the right one.
- **Sessions are keyed by peer identity, not by transport path.** A mesh session is end-to-end and survives changing relay paths. The application AEAD AAD must exclude any field a relay mutates (notably **TTL**).
- **Everything that can be encrypted is encrypted.** Only ANNOUNCE and the Noise handshake travel in the clear — every other packet is a sealed `secure` envelope, *including* the sync exchange (the seen-filter rides as the `syncFilter` `SecureFrame` content type, sealed to the peer's session, TTL 1, over either transport). What a node has seen is not put on the air in the clear just because those packetIds also appear in packet headers: the session already exists when sync runs, so there is no reason to transmit plaintext.
- **ANNOUNCE is the one exception** — it is a neighbor-local, never-relayed presence broadcast that *is* about identity, so it carries the pubkey and a payload-level signature in the clear and is verified hop-locally.

## BLE Discovery & Identity

Every device advertises a public-key-derived Grassroots service UUID: a fixed Grassroots prefix plus the first 8 bytes of SHA-256(domain string | public key | rotation slot), the slot advancing every 15 minutes so the advertisement is not a durable tracking handle. Rotation currently sits behind a kill switch for hardware testing, which pins the slot at 0 — the derivation is unchanged either way. The UUID is only a discovery hint, never an authorization proof. Identity is established by the **self-signed ANNOUNCE** — a neighbor-local (non-relayed) broadcast whose payload carries the full public key, nickname, and an Ed25519 signature over that payload (the packet header itself signs nothing). In open cold-call mode, nearby unknown BLE peers may complete ANNOUNCE; in closed mode, unknown nearby peers do not get ANNOUNCE, and friend-only metadata is sent only after a verified ANNOUNCE authenticates an accepted friend.

## Dual-Role BLE Is Mandatory

Every BLE pair must converge to a **dual-role connection**: two GATT legs, with each device central on one leg and peripheral on the other. Never ship a design that intentionally leaves a pair single-link. This requirement is inviolable.

Platform asymmetries are solved by choosing **who initiates each leg** — ordering, pair reform — never by abandoning a leg. The one measured constraint is that an iOS central cannot open the *second* link toward an Android it is already linked with: the connect sits in `connecting` and never reports, until it times out. Leg order is decided **platform-neutrally**, by comparing the two service UUIDs, and the advertised local name is the nickname — there is no platform marker on the air and no iOS-specific arbitration.

When a platform behavior is **unknown** (e.g. whether an iOS↔iOS reverse leg works), attempt it and let hardware decide — do not suppress it on extrapolation. A single-link pair is acceptable only as a *transient* state that the transport keeps trying to upgrade, or where hardware has *measurably* refused the second leg and the only remaining lever is initiator order.

## Well-Connected Friends & Hole-Punching

Most mobile devices sit behind NAT and cannot accept incoming UDP connections from the public Internet. A **well-connected** device is one that has a globally routable public address — it can be reached directly by anyone.

Well-connected friends play a special role: they act as **signaling relays** to help two NAT'd peers find each other. The flow is:

1. Each device registers its current address with its well-connected friends.
2. When peer A wants to reach peer B, A asks a mutual well-connected friend for B's address.
3. The friend sends each side a `PUNCH_INITIATE` carrying the other's observed address. Both peers begin spraying small UDP *punch* packets at that address, opening the outbound NAT mapping on each side.
4. The connection is then opened by a **deterministic initiator** — the peer with the lexicographically smaller public key dials the UDX stream (by sending a signed ANNOUNCE to the punched address) while the other side keeps punching until the stream lands. This is an initiator/responder split, **not** a clock-synchronized simultaneous send. Once the path is open, A and B communicate directly and the well-connected friend leaves the path.

> Implementation note: the burst-sending is `HolePunchService` (it only sprays `BCPU`+pubkey packets on a fixed interval/duration — no coordination logic of its own). Initiator selection, `PUNCH_INITIATE` handling, and the connect are owned by the coordinator (`GrassrootsNetwork`) and `SignalingService`. Keep this split in mind: no single class performs "the hole-punch."

**Important:** Well-connected friends relay *signaling metadata* (addresses, punch coordination), never third-party message content — the **UDP/Internet transport stays direct point-to-point**. Multi-hop content relay happens only on the BLE mesh (see Opportunistic Mesh), and even there relays carry sealed bytes, not readable content. What UDX *does* move is a connected peer's OWN buffered packets, which is a delivery to the endpoint rather than a relay through it.

**UDP signaling is friend-only.** This trust boundary is specific to Internet hole-punch coordination and is *separate* from the BLE mesh's open relay. A well-connected device only coordinates hole-punches between peers that are both its friends: it only registers friends' addresses in its address table, only responds to address queries for friends, and only sends PUNCH_INITIATE to friends. (The BLE mesh, by contrast, relays for arbitrary recipients — but it never exposes addresses or content, only forwards sealed packets by recipient ID.)

## Redux Architecture

All peer and transport state lives in an immutable Redux store (`AppState`). Key slices: `PeersState` (discovered BLE devices + identified peers), `TransportsState` (per-transport lifecycle + public address), `MessagesState`, `FriendshipsState`, `SettingsState`. UI reads from the store and subscribes to changes. Actions describe events; reducers produce the next state. No mutable singletons.

The Redux state is a strict projection of facts emitted by the transport layers — never an inference. Reducers must not synthesize state from "I haven't heard from X in N seconds" heuristics; that's the transport layer's job to surface as an explicit event (path failed, UDX session torn down, etc.).

## Transport Layer

Two transports are available, toggled independently in settings:

- **Bluetooth (BLE)** — local, no Internet required. Preferred when both are available.
- **Internet (UDP via UDX)** — global reach, requires Internet. Uses hole-punching for NAT traversal.

The `TransportState` lifecycle for each transport is: `uninitialized → initializing → ready → active` (plus `error` and `disposed`). A transport is "usable" when it is `ready` or `active`.

User-facing UI strings should say "Internet", not "UDP" or internal protocol names.

## One Address Per Connection, Multiple Candidates Per Peer

Per **connection**, exactly one address pair is in use — there is no per-message address selection or mid-stream address switching. But a device MAY advertise multiple address **candidates** in ANNOUNCE (e.g. public IPv4, public IPv6, link-local IPv6 for the same LAN), and each peer pair selects the candidate that actually works between them: link-local on the same LAN, public IPv6 across the Internet, IPv4 as a fallback. Once a connection is established on a candidate, the pair sticks to that candidate until the path breaks.

The primary public address is discovered via an external service (e.g. seeip.org). Link-local candidates are scoped to the local network and never reach the public Internet; they exist so two devices on the same LAN can connect directly without traversing NAT.

## Peer Address Persistence

Never unilaterally clear a peer's stored UDP address. Update it when a new valid address arrives (from ANNOUNCE, signaling, or observation), and clear it only when the peer explicitly tells us they no longer have one. Stale peer cleanup, our-side disconnects, and transport restarts must not null out `udpAddress` — it is the last known location and the only way to attempt reconnection.

**Unfriending is the one exception, and it is a deliberate one.** Removing a friend nulls `udpAddress` and empties the candidate set, because an address is the standing ability to reach a person on the Internet and withdrawing friendship is exactly the act of giving that up. It is not a connectivity event, which is what the rule above is about — every one of those (a drop, a sweep, a restart) keeps the address. The Noise session is NOT cleared with it: a session is a transport fact keyed by identity and survives a friendship change untouched.

## Transport Independence

BLE and UDP are independent transports. Disabling or losing one must have **zero effect** on the other's connection state, peer reachability, or online status. A peer connected via UDP remains online regardless of BLE state. The stale peer logic, the UI, and the reducer must all respect this: never let a BLE disconnection degrade UDP-derived state.

Application-level callbacks (`onPeerConnected`, `onPeerDisconnected`) report consolidated end-to-end reachability, not per-transport events: they fire only when the overall reachable/unreachable state changes (transitions to/from zero live transports). Losing one of two live transports does not fire a disconnect — it only fires when the *last* transport drops.
